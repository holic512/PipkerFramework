# 权限配置说明

本项目只做页面路由级和后端 API 级权限控制，不实现前端按钮级鉴权。权限唯一裁决来源是数据库；Sa-Token 只负责 Bearer 会话和统一 Filter 入口。

## 关系与角色规则

```text
system_user → system_user_role → system_role → system_role_permission → system_permission
                                                                  ├─ PAGE → system_menu
                                                                  └─ API  → system_api_resource
```

| 对象 | 作用 |
| --- | --- |
| `PAGE` 权限 | 控制一个 `MENU` 页面是否出现在 `/api/auth/me` 的菜单树中，并决定前端是否注册、访问该页面路由。 |
| `API` 权限 | 控制一个或多个受保护 HTTP 资源；资源由 HTTP 方法和 Spring MVC 路径模板定义。 |
| `SUPER_ADMIN` | 自动拥有所有启用的 `PAGE`、`API` 权限；不维护角色权限关联。 |
| 其他角色（含 `ADMIN`） | 合并所有启用角色在 `system_role_permission` 中显式授予的权限。 |

角色、权限、菜单或用户被禁用后，不会再进入下一次缓存刷新得到的授权结果。

## 新增功能的配置顺序

在同一个 Liquibase 增量 changeset 中完成以下配置：

1. 新增 `PAGE` 权限，例如 `order:list:page`。
2. 新增 `MENU`，将 `system_menu.permission_code` 指向该 `PAGE` 权限，并填写稳定的 `route_path`、`route_name`、`component_key`。
3. 新增本功能的 `API` 权限，例如 `order:list`、`order:detail`。
4. 在 `system_api_resource` 中为每个受保护接口登记 `permission_id + http_method + path_pattern`，例如 `GET /api/orders/{id}`。
5. 将所需 `PAGE` 和 `API` 权限写入目标角色的 `system_role_permission`。

页面权限和接口权限必须分开编码。一个页面可调用多个 API；一个 API 权限也可映射多个 HTTP 资源。

## API Filter 规则

- 只有 `GET /api/ping` 和 `POST /api/auth/login` 是匿名接口，新增匿名接口必须显式加入 `pipker.security.auth.public-routes`。
- 其他 `/api/**` 请求先验证登录态，再以 `HTTP 方法 + MVC 路径模板` 查找启用的 `API` 资源。
- 必须唯一命中一条规则且当前用户拥有其权限；未登记、方法不匹配、路径模板重叠、权限不足都返回 `AUTH_FORBIDDEN`。
- 不使用 `@SaCheck*` 注解，也不允许 Controller 内自行执行权限判断；所有接口保护统一在 Filter 完成。
- 路径模板采用 Spring MVC 形式，如 `/api/orders/{id}`；不要为同一请求设计会同时命中的模板。

## 缓存与迁移

`pipker.security.auth.authorization-cache-ttl` 默认是 `60s`，本地缓存用户授权快照和启用 API 资源规则；`authorization-cache-maximum-size` 默认是 `10000`。数据库直接改权后，每个应用实例最迟在自身缓存到期后生效；多实例不会自动广播清缓存。

009 迁移已删除 `system_role_menu`、`BUTTON` 权限和按钮菜单，以及开发 Route Manifest。已有生产库执行前请先备份；不要改写已执行的 001–008 历史 changeset。
