# 权限配置说明

本项目提供页面路由级和后端接口级权限控制，不实现前端按钮级鉴权。页面菜单授权和接口权限授权是两套独立关系：菜单决定页面是否进入当前账户的导航和动态路由，接口权限决定 MVC 接口是否允许执行。

## 运行时权限来源

`PermissionEnum` 是当前运行时接口权限点的唯一有效定义来源。每个接口通过 `@Permission(PermissionEnum.X)` 声明所需权限，MVC `PermissionAuthorizationInterceptor` 在请求进入控制器前读取注解，并使用当前用户授权快照中的权限编码进行判断。

权限编码统一使用 `system:resource:action` 格式，例如：

```text
system:authorization:view
system:role:manage
system:route:view
system:route:manage
system:user:view
system:user:manage
```

`PermissionRegistry` 在应用启动时按 `PermissionEnum` 的声明顺序加载权限点，校验编码重复，并过滤角色关联中已经从枚举移除的历史编码。角色表 `system_role_permission.permission_code` 保存的是枚举权限编码，不负责定义权限本身；角色管理保存接口权限时也只接受当前枚举中存在的编码。

## 关系与角色规则

```text
system_user → system_user_role → system_role
                                  ├─ system_role_menu → system_menu（页面路由）
                                  └─ system_role_permission（PermissionEnum 编码）

历史兼容结构：system_permission ← system_api_resource
```

| 对象 | 作用 |
| --- | --- |
| `system_role_menu` | 页面路由授权来源。角色关联一个 `MENU` 后，拥有该角色的用户才会收到、注册和访问该页面路由。 |
| `system_role_permission` | 保存角色选择的当前 Java `PermissionEnum` 编码；只授予后端 MVC 接口权限。 |
| `SUPER_ADMIN` | 自动拥有全部启用页面路由和全部当前有效枚举权限，不维护其角色菜单或角色权限关联。 |
| 其他角色 | 用户的多个启用角色按并集获得页面菜单和接口权限，不存在拒绝规则或优先级。 |

目录 `DIRECTORY` 只用于组织菜单树，不写入角色菜单关联。系统会为获授权页面自动补齐其可见祖先目录。禁用角色、禁用菜单或隐藏菜单不会进入下一次授权快照。

## 权限点目录页

权限点页面位于“系统管理 → 权限点”，页面只读展示当前 `PermissionEnum` 目录，不提供新增、编辑、删除、保存或角色授权操作。页面通过冒号分隔符将权限编码转换为命名空间树，并保留枚举声明顺序；角色接口权限弹窗使用相同的冒号分组规则。

页面调用以下只读接口获取扁平权限点列表：

```text
GET /api/admin/permissions
```

该接口复用 `system:role:manage` 作为访问权限，因此普通角色需要同时拥有“系统管理 → 权限点”菜单关系和 `system:role:manage` 接口权限；超级管理员继续自动拥有两者。接口不分页、不查询数据库权限定义，也不提供权限点 CRUD。

## 页面与接口授权配置

`SUPER_ADMIN` 登录后可在“系统管理 → 角色管理”中，对指定角色打开“页面权限”并勾选页面菜单；保存即可全量替换该角色的页面路由。超级管理员始终全量可见，页面中只读。

新增一个业务页面时，在追加式 Liquibase changeset 中完成：

1. 新增 `MENU`，填写稳定的 `route_path`、`route_name`、`component_key`，并确保前端已有 `src/modules/<component_key>.vue`。
2. 在角色管理的“页面权限”中为目标角色勾选该菜单；也可以在部署数据中直接写入 `system_role_menu`。
3. 在 `PermissionEnum` 中新增接口权限，使用 `system:resource:action` 编码，并在接口或控制器上增加 `@Permission`。
4. 将新编码写入目标角色的 `system_role_permission`，或通过角色管理页的“接口权限”弹窗保存。

页面菜单授权不会自动授予接口权限；页面调用接口所需的权限必须单独配置。接口权限也不会自动创建页面菜单。

## 历史兼容结构

`system_permission` 和 `system_api_resource` 是历史兼容结构，保留既有表、外键和数据以兼容旧数据与持久化映射，但不能再被描述为当前 MVC 注解授权的唯一来源。当前请求授权路径是：登录态 → 当前角色授权快照 → `@Permission(PermissionEnum.X)` → 枚举编码匹配。

已有数据库的权限编码迁移通过追加式 changeset 执行，只转换当前六个已确认的旧连字符编码；未知或已经失效的历史编码保持原样，并在角色接口权限详情的 `historicalPermissionCodes` 中只读展示。不要修改已经执行的历史 changeset。

## 会话与缓存

`pipker.security.auth.authorization-cache-ttl` 默认是 `60s`，本地缓存用户授权快照。通过角色管理的页面权限或接口权限保存后，本实例会立即清除受影响的授权快照；直接改数据库或其他实例最多在各自缓存到期后生效，当前没有跨实例缓存广播。

只有健康检查和登录接口匿名可用；其他 `/api/**` 请求先验证登录态，再由 MVC 权限拦截器处理带有 `@Permission` 的接口。未认证、无权限和接口业务错误继续使用统一 API 响应码。
