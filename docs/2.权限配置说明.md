# 权限配置说明

本项目只做页面路由级和后端 API 级权限控制，不实现前端按钮级鉴权。数据库是唯一授权来源；Sa-Token 只负责 Bearer 会话和统一 Filter 入口。

## 关系与角色规则

```text
system_user → system_user_role → system_role
                                  ├─ system_role_menu → system_menu（页面路由）
                                  └─ system_role_permission → system_permission(API) → system_api_resource
```

| 对象 | 作用 |
| --- | --- |
| `system_role_menu` | 页面路由授权来源。角色勾选一个 `MENU` 后，拥有该角色的用户才会收到、注册和访问该页面路由。 |
| `system_role_permission` | 仅授予后端 `API` 权限。一个 API 权限可映射多个 HTTP 资源。 |
| `SUPER_ADMIN` | 自动拥有所有启用可见菜单和所有启用 API 权限；不维护其角色菜单或角色权限关联。 |
| 其他角色 | 用户的多个启用角色按并集获得页面菜单和 API 权限，不存在拒绝规则或优先级。 |

目录 `DIRECTORY` 只用于组织菜单树，不写入角色菜单关联。系统会为获授权页面自动补齐其可见祖先目录。禁用角色、禁用菜单或隐藏菜单不会进入下一次授权快照。

## 配置页面与新增功能

`SUPER_ADMIN` 登录后可在“系统管理 → 角色管理”中，对指定角色打开“页面权限”并勾选页面菜单；保存即可全量替换该角色的页面路由。超级管理员始终全量可见，页面中只读。

新增一个业务页面时，在同一个 Liquibase 增量 changeset 中完成：

1. 新增 `MENU`，填写稳定的 `route_path`、`route_name`、`component_key`，并确保前端已有 `src/modules/<component_key>.vue`。
2. 在角色管理的“页面权限”中为目标角色勾选该菜单；也可以在部署数据中直接写入 `system_role_menu`。
3. 新增本功能需要的 `API` 权限，例如 `order:list`、`order:detail`。
4. 在 `system_api_resource` 中登记每个受保护接口的 `permission_id + http_method + path_pattern`，例如 `GET /api/orders/{id}`。
5. 将 API 权限写入目标角色的 `system_role_permission`。

页面菜单授权不会自动授予 API 权限；页面调用接口所需的 API 权限必须单独配置。

## API Filter 规则

- 只有 `GET /api/ping` 和 `POST /api/auth/login` 是匿名接口；新增匿名接口必须显式加入 `pipker.security.auth.public-routes`。
- 其他 `/api/**` 请求先验证登录态，再以 `HTTP 方法 + MVC 路径模板` 查找启用 API 资源。
- 必须唯一命中一条规则且当前用户拥有其 API 权限；未登记、方法不匹配、路径模板重叠或权限不足都返回 `AUTH_FORBIDDEN`。
- 不使用 `@SaCheck*` 注解，也不允许 Controller 内自行执行权限判断；所有接口保护统一由 Filter 完成。
- 路径模板使用 Spring MVC 形式，如 `/api/orders/{id}`；不要定义可能同时匹配同一请求的模板。

## 缓存与迁移

`pipker.security.auth.authorization-cache-ttl` 默认是 `60s`，本地缓存用户授权快照和启用 API 资源规则；`authorization-cache-maximum-size` 默认是 `10000`。通过角色管理的“页面权限”保存后，本实例会立即清除用户授权快照；直接改数据库或其他实例最多在各自缓存到期后生效，当前没有跨实例缓存广播。

`009` 已删除按钮权限、按钮菜单和开发 Route Manifest；`010` 恢复 `system_role_menu` 并删除 `PAGE` 权限和 `system_menu.permission_code`。生产迁移前请备份数据库，且不要改写已经执行的历史 changeset。
